# Address_matching_GPB_1 — компонентное сопоставление адресов

Развитие проекта **Address Matching**: сопоставление адресов с опечатками, сокращениями, пропущенными пробелами и изменённым порядком компонентов с эталонным справочником.

**Репозиторий:** [AlexSDem/Address_matching_GPB_1](https://github.com/AlexSDem/Address_matching_GPB_1).  
**Основа сравнения:** исходный архив `Address_matching_GPB_base-main.zip`.  
**Состояние проверки:** 17.09.2026, код новой версии на коммите `a4fdf6f`; изменения в этом README описывают существующую реализацию и не исправляют её код.

Проект ИТМО AI Talent Hub. Участники исходного проекта: Дарья Вегера и Александр Демьянов. Руководитель: Кристина Желтова. [Первоначальный отчёт](docs/README.md) сохранён отдельно и относится к baseline.

**Текущий результат — работающий исследовательский прототип.** Реализованы разбор адреса, гибридное ранжирование, контролируемые аугментации, оценка top-1 и интерфейс Streamlit. Обработка требований подтверждена на небольших демонстрационных наборах. Качество на независимых реальных данных и польза дополнительного реранкера пока не установлены.

## 1. Отличия от базового репозитория

В последнем столбце разделены **польза для сопоставления адресов**, **польза для проверки качества** и **удобство работы**. Не каждое изменение повышает точность: интерфейс, метрики и организация кода решают другие задачи. Описанные механизмы проверены в составе прототипа; вклад каждой отдельной правки в прирост метрик не выделялся.

**Что изменилось в измеренных результатах:** на тех же 25 ручных кейсах HitRate@1 среди 16 запросов с единственным правильным ответом вырос с **62.5% до 100%**; на 120 синтетических запросах — с **97.4% до 100%** среди 114 однозначных запросов. Это эффект новой конфигурации в целом на демонстрационных данных, а не доказательство пользы каждой строки таблицы или такого же улучшения в эксплуатации. Состав наборов, остальные метрики и ограничения сравнения приведены в разделе 5.

Сокращения и устойчивость к перестановкам **частично присутствовали уже в baseline**. В новой версии добавлены их компонентная обработка и специальная проверка, поэтому некорректно считать эти возможности полностью новыми с нуля.

Исходный алгоритм сохранён в [src/baseline.py](src/baseline.py), исходная нормализация — в [src/baseline_normalize.py](src/baseline_normalize.py). Сверка с исходным архивом подтвердила сохранение их логики: в matcher изменён путь импорта нормализатора. Старый импорт `from src.matcher import AddressMatcher` остаётся доступным. Новый алгоритм вызывается через `HybridAddressMatcher`.

## 3. Как работает новая версия

### Разбор

[src/address_normalize.py](src/address_normalize.py) и [src/parser.py](src/parser.py) используют регулярные выражения, маркеры и словарь из эталонного корпуса. Это парсер на правилах, а не обученная NER-модель. Алиасы применяются только к полю города.

Сокращённое название улицы раскрывается при единственном варианте в контексте региона, города и типа улицы. Неоднозначные варианты дают предупреждение; неоднозначное `пр.` автоматически не превращается в проспект.

### Поиск и оценка пары

[src/hybrid.py](src/hybrid.py) объединяет top-30 TF-IDF кандидатов с пересечением доступных точных компонентных блоков. Дополнительный блок позволяет учитывать, например, одноимённые города даже за пределами текстового top-k. Внутреннее использование нескольких кандидатов нужно для поиска и проверки неоднозначности; целевой результат и основные метрики относятся к **top-1**.

Для указанных в запросе компонентов:

```text
component_score = Σ(weight[field] × similarity[field]) / Σ(weight[field])
score = 0.85 × component_score + 0.15 × cosine_similarity
```

Сходство значений компонентов — RapidFuzz `ratio` после удаления пробелов. Веса:

| Компонент | Вес |
|---|---:|
| Регион | 2 |
| Город | 3 |
| Район | 0.3 |
| Тип улицы | 0.5 |
| Улица | 3 |
| Дом | 3 |
| Корпус | 2 |
| Строение | 2 |
| Квартира | 1 |

Обнаруженные несовпадения региона, типа улицы, дома, корпуса, строения и квартиры запрещают автоматическое принятие. Для города допускается буквенная опечатка при similarity ≥ 0.88, но цифровые части должны совпадать. Для улицы similarity < 0.68 считается конфликтом. Район — мягкий признак. Указанное поле, отсутствующее в эталоне, считается непроверенным.

По умолчанию auto-match требует: город + улицу + дом, отсутствие предупреждений и конфликтов, `score ≥ 0.84`, отрыв от следующего допустимого кандидата `≥ 0.06`. Если допустимый кандидат один, margin равен его score. Несколько кандидатов с полностью совпавшими указанными компонентами дают неоднозначность.

**Score не является вероятностью правильного ответа.** Правила действуют на извлечённых компонентах: ошибки самого парсера способны обойти последующие проверки, см. раздел 6.

### Результат

| Статус | Смысл |
|---|---|
| `accepted` | Совпадение автоматически принято; заполнены `best`, `best_id` |
| `review` | Требуется уточнение или ручная проверка |
| `no_match` | Надёжное совпадение не установлено; это не доказательство отсутствия адреса в справочнике |

`candidate` и `candidate_id` — диагностический top-1, который может быть заполнен даже при отказе. Не используйте его как исправленный адрес без проверки статуса.

Причины решения: `conflict_*` — конфликт, `unverified_*` — поле не подтверждается эталоном, `ambiguous_*` — неоднозначность, `incomplete_identity` — недостаточно полей, `low_score` — низкий score, `small_margin` — малый отрыв.

### Реранкер

По умолчанию `rerank_enabled=False`. Дополнительный ранкер можно передать как функцию `(query, candidates) -> scores`, возвращающую по одному конечному score в [0, 1]. Маршрут разрешён при малом отрыве и наличии нескольких допустимых кандидатов, если нет предупреждений, неполной идентичности и обнаруженных конфликтов. После вызова используется `0.8 × hybrid_score + 0.2 × reranker_score` и снова проверяются пороги.

Готовой нейронной модели и обучения нет. Проверка, что реранкер не вызывается при конфликте, **не доказывает**, что его применение улучшает качество на допустимых парах. В baseline слово rerank обозначает переупорядочивание по RapidFuzz, а не нейронный cross-encoder.

## 4. Аугментации и метрики

[src/augmentation.py](src/augmentation.py) и [scripts/generate_queries.py](scripts/generate_queries.py) создают:

- чистый вариант и перестановку целых компонентов;
- отсутствие пробелов;
- типовые сокращения и укороченные названия улиц;
- удаление региона/района;
- перестановку соседних букв в названии улицы;
- отдельно — обмен номера дома и корпуса с повторным определением допустимого ответа.

Многословные названия `Нижний Новгород`, `8 Марта` и значения связанных компонентов не перемешиваются случайно. Если изменение образует другой существующий адрес, правильным ответом становится его ID; отсутствие единственного ответа обозначается пустым `true_id`.

Разметка генерируется из компонентов эталона, без использования предсказанного ранга. Однако при неструктурированном справочнике компоненты эталона тоже извлекаются парсером: это **не независимая ручная разметка** и возможен общий источник ошибок.

`source_id` объединяет варианты исходного адреса; split 60/20/20 выполняется по этим группам. Эталон целиком остаётся в поисковом индексе. Обучаемого ранкера нет, train сейчас резервный. Группировка не исключает близкие сущности и одинаковые неоднозначные запросы в разных split — для строгой оценки их тоже нужно контролировать.

| Метрика | Что измеряет |
|---|---|
| `hitrate_at_1` | Верный ID top-1 / число запросов с единственным `true_id`, до порогового отказа. В этой постановке совпадает с Accuracy@1 |
| `pair_precision`, `pair_recall`, `pair_f1`, `pair_accuracy` | Бинарное решение для пары «запрос, выбранный top-1»: истинная метка 1 при совпадении ID, предсказание 1 при `accepted` |
| `resolution_recall` | Правильные принятые ответы / все запросы с единственным `true_id`; учитывает потерю правильного адреса на ранжировании |
| `resolution_f1` | F1 между precision принятых связей и resolution recall |
| `coverage` | Доля автоматически принятых запросов, включая ошибки |
| `decision_accuracy` | Правильный принятый ID либо корректный отказ при отсутствии однозначного ответа |

Pair recall и resolution recall различаются: неверный top-1 можно правильно отклонить как отрицательную пару, но задача сопоставления всё равно останется нерешённой. При ошибочно принятом чужом ID возникает ложная связь и теряется правильная связь.

Пустой `true_id` объединяет неизвестные и неоднозначные запросы; различайте их через `category`. В неоднозначном случае отрицательная метка означает «нельзя автоматически выбрать единственный адрес», а не обязательно «кандидат заведомо не имеет отношения к запросу». Несколько допустимых ID пока не поддерживаются. При нулевом знаменателе PR/F1 равны 0; HitRate без однозначных запросов — null.

## 5. Что проверено и чего результаты не доказывают

17.09.2026 на указанной версии повторно выполнены **45 тестов: все прошли**. Это 36 проверок основного решения и 9 проверок OSM-загрузчика/ноутбука. Загрузка в тестах имитируется; live-выгрузка OSM и запуск Streamlit в рамках этой проверки не выполнялись. Исторический [отчёт](reports/EXPERIMENTS.md) содержит более ранние проверки интерфейса и указывает прежнее число 36, до добавления загрузчика.

Повторный запуск оценки воспроизвёл результаты ниже. **Оба набора использовались при разработке и не являются независимым тестом.** Эталон — всего 17 демонстрационных записей.

| Набор | Алгоритм | HitRate@1 | Pair precision | Pair recall | Pair F1 | Resolution recall | Coverage |
|---|---|---:|---:|---:|---:|---:|---:|
| Ручные кейсы, 25 | Baseline | 0.625 | 0.778 | 0.700 | 0.737 | 0.438 | 0.360 |
| Ручные кейсы, 25 | Hybrid | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 0.640 |
| Синтетические запросы, 120 | Baseline | 0.974 | 0.964 | 0.955 | 0.959 | 0.930 | 0.917 |
| Синтетические запросы, 120 | Hybrid | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 0.950 |

У ручных кейсов 16 однозначных запросов и 9 запросов без единственного ответа; у синтетики — 114 и 6. HitRate рассчитывается только по однозначным запросам. Например, coverage 0.64 для ручного набора соответствует 16 принятым запросам из 25.

Артефакты: [ручные метрики](reports/metrics.csv), [ручные предсказания](reports/predictions.csv), [синтетические метрики](reports/synthetic/metrics.csv), [синтетические предсказания](reports/synthetic/predictions.csv).

Ограничения сравнения:

- 100% на этих примерах означает прохождение текущих сценариев, а не качество 100% на реальных адресах.
- Порог baseline равен 0.85, hybrid — 0.84 с margin 0.06; топ-k и признаки тоже различаются. Это сравнение конфигураций, не изолированная оценка вклада каждого механизма.
- Нет абляций: отдельно отключить алиасы, восстановление пробелов, компонентные веса и проверки конфликтов.
- Нет независимого сравнения ON/OFF дополнительного реранкера, нагрузочного теста и оценки точности извлечения каждого поля.
- Исходные 0.96 на 100 зашумлённых запросах к 6 448 адресам приведены в старом отчёте. Сам CSV в исходном архиве отсутствует; эти показатели нельзя напрямую сравнивать с новой таблицей.

## 6. Известные ограничения и порядок следующих работ

**При дополнительной проверке найдены ошибки, не покрытые текущими 45 тестами:**

| Запрос к демосправочнику | Текущее поведение | Почему это проблема |
|---|---|---|
| `г. Москва, г. Санкт-Петербург, Невский проспект, д. 5` | `accepted`, ID `spb5` | Парсер сохраняет последнее явно указанное значение города и теряет противоречие |
| `Красноярск, ул. Ленина Неизвестная, д. 25` | `accepted`, ID `kr25` | Поиск известного названия улицы может отбросить дополнительный нераспознанный текст |

Следовательно, утверждение «любые конфликтные адреса всегда отклоняются» неверно. Код в этой версии не исправлен; примерные успешные сценарии не заменяют проверку негативных случаев.

Приоритет дальнейших работ:

1. Добавить регрессионные тесты для этих ошибок; сохранять повторные значения компонентов и нераспознанные фрагменты, чтобы они влияли на решение.
2. Собрать независимые реальные запросы и эталонные ответы, включая отсутствующие адреса, одноимённые города, неоднозначность и комбинации шумов. Загрузка OSM создаёт эталон, но сама по себе не создаёт независимый benchmark.
3. Расширить географию OSM и словарь алиасов. Текущий загрузчик по умолчанию охватывает только два района Москвы и один район Санкт-Петербурга; он не проверяет все географические случаи руководителя на реальных данных.
4. Зафиксировать разбиение; подобрать пороги обоих методов на validation при одинаковом требовании precision. Сравнить coverage и resolution recall на test, оценить неопределённость метрик.
5. Провести абляции компонентов и правил. Для синтетики из неструктурированных строк вручную проверить разбор эталона.
6. При наличии времени подключить конкретный реранкер и сравнить ON/OFF на заранее фиксированном маршруте. Fine-tuning рассматривать отдельно после накопления размеченных пар.

Дополнительно: не гарантируются владения, участки, километры трасс, сложные литеры, административная иерархия и неизвестные склеенные топонимы. Квартира, указанная в запросе при её отсутствии в эталоне, препятствует автоматическому принятию. Производительность на сотнях тысяч/миллионах адресов не измерялась. Весовые коэффициенты и score не калиброваны как вероятности.

## 7. Быстрый запуск

Python 3.10–3.12; проверка выполнена на Python 3.12. GPU, внешние языковые модели и API-ключи не требуются.

```bash
git clone https://github.com/AlexSDem/Address_matching_GPB_1.git
cd Address_matching_GPB_1
python -m venv .venv
# macOS / Linux:
source .venv/bin/activate
# Windows PowerShell: .venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m streamlit run app.py
```

Откройте адрес, который выведет Streamlit. По умолчанию загружается [демосправочник из 17 записей](data/reference_demo.csv). Для своих адресов загрузите CSV через боковую панель. Примеры:

- `Красноярск, ул. Ленина 25` — совпадение;
- `г.Красноярск,ул.Ленина,д.25` — пример без пробелов;
- `г. Горький, ул. Ленина, д. 10` — исторический алиас;
- `Железногорск, ул. Ленина 25` — уточнение региона;
- `Москва, ул. Ленина 10к2` — корпус;
- `Москва, ул. Ленина 999` — отсутствие надёжного совпадения.

Для пакетной обработки нужен CSV с колонкой `query`. Результат можно скачать из приложения. Диагностические кандидаты доступны в раскрывающемся блоке, но основной ответ — один принятый адрес или отказ.

## 8. Справочник и загрузка OSM

Минимум — непустая колонка `address` либо `united_addr`. Рекомендуемые строковые колонки: `id,region,city,street_type,street,house,building,structure`, опционально `district,apartment`. Поддерживаются `addr:city`, `addr:street`, `addr:housenumber`.

ID должны быть уникальными. Если их нет, используются номера строк; они нестабильны при перестановке/изменении файла. Дубли одной сущности с разными ID лучше объединить заранее. Эталон с явными компонентами предпочтительнее неструктурированных строк.

```python
from src.io import ROOT, read_reference, read_aliases
from src.hybrid import HybridAddressMatcher

reference = read_reference(ROOT / 'data/reference_demo.csv')
matcher = HybridAddressMatcher().fit(reference, read_aliases())
result = matcher.match_one('Красноярск, ул. Ленина 25')
print(result.status, result.best_id, result.best, result.reasons)
```

Если `reference_osm.csv` отсутствует:

```bash
python -m pip install -r requirements-osm.txt
python scripts/download_reference_osm.py
```

Настройки районов — [data/osm_places.json](data/osm_places.json). Пути по умолчанию определяются относительно проекта, без жёсткого `/content/Address_matching_GPB`. Загрузчик сохраняет `reference_osm.csv` и `reference_osm.meta.json` в корень. Это новая выгрузка OSM, её размер может отличаться от исходных 6 448 записей.

| Параметр | Назначение |
|---|---|
| `--refresh` | Пересоздать CSV, минуя HTTP-кеш OSMnx |
| `--places path.json` | Свой список объектов `query`, `city`, опционально `region` |
| `--output path.csv` | Другое место сохранения; отсутствующие родительские папки создаются |
| `--timeout 180` | Таймаут одного HTTP-запроса, не суммарного процесса |
| `--allow-partial` | Явно разрешить неполную выгрузку |

При обычном повторном запуске существующий CSV используется без скачивания. При изменении списка районов нужны `--refresh` или новый output. Сбой части районов не заменяет основной CSV: доступная часть сохраняется в `reference_osm.partial.csv`, ошибки — в `reference_osm.attempt.json`, код завершения равен 1. Без метаданных полнота старого CSV не подтверждается.

Город из OSM имеет приоритет над fallback-городом из конфигурации. Пустые улицы/дома удаляются, повторы объединяются по нормализованным компонентам. `osm_ids` и `source_places` сохраняют происхождение. `id` — хеш компонентов, а не официальный идентификатор ГАР/ФИАС.

Для **Google Colab** откройте [notebooks/colab_quickstart.ipynb](notebooks/colab_quickstart.ipynb): поиск/скачивание проекта → установка → тесты → загрузка OSM → проверка модели → скачивание CSV. После сброса сессии выполняйте с начала. Для нестандартного расположения задайте `PROJECT_DIR` в первой ячейке. OSM требует доступа к сети; встроенный демосправочник — нет.

## 9. Тесты и воспроизведение экспериментов

Из корня проекта:

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q
python scripts/evaluate.py
python scripts/generate_queries.py --reference data/reference_demo.csv --output data/generated_queries.csv
python scripts/evaluate.py --queries data/generated_queries.csv --output reports/synthetic
```

Формат запросов: `query,true_id,category`; для калибровки также `source_id,split`. Пустой `true_id` означает отсутствие единственного допустимого автоматического ответа. Результаты: `predictions.csv`, `metrics.csv`, `config.json`. Пути в сохранённых старых `config.json` могут относиться к среде прежнего запуска; команды выше создают новые отчёты в вашей среде.

```bash
python scripts/calibrate.py --reference data/reference_demo.csv --queries data/generated_queries.csv --min-precision 0.98
```

Сетка перебирает threshold и margin **только на validation**. Результат — `reports/calibration/selected.json`. Если допустимых параметров нет, статус `no_feasible_configuration`. Выбранные пороги не меняют автоматически конструктор модели или настройки Streamlit.

Пример применения параметров, выбранных в сохранённом демоэксперименте:

```bash
python scripts/evaluate.py --queries data/generated_queries.csv --split test --threshold 0.92 --margin 0.02 --output reports/test
```

После своей калибровки подставьте собственные значения. Разработчик уже использовал весь демонабор при отладке, поэтому его test-часть не считается независимой финальной оценкой. Точечное значение precision на небольшом validation не гарантирует заданную точность на новых данных.
